## 01数据存在哪? - MySQL(存储)

1. # MySQL 是像 Excel 那样以表格形式存储数据的. 但是它可以轻轻松松承载什么数量级的数据?
MySQL 使用表格存储，单表可支撑千万级数据，分库分表后可支持亿级。文中几十万条用户、笔记数据对 MySQL 属于小规模数据。
2. # MySQL 是怎么做到能轻松承载大量数据, 并且查询, 修改它们时仍然很快的?
MySQL 依靠索引快速定位数据(类似书本目录)，结合存储引擎(数据按页组织)、内存缓存优化磁盘 IO，不需要加载全部文件，所以大数据量下查询修改依旧很快。
（可以理解为查字典）

## 02怎么查得快? - Redis（查询）

1. # Redis 为什么这么快？
Redis 主要把数据放在内存中读写，不需要频繁访问慢速磁盘；采用键值对简单存储结构，没有 MySQL 复杂的表、事务解析开销；再加上单线程模型、IO 多路复用，查询速度远快于 MySQL。
2. # MySQL 一行数据，以什么形式存入 Redis 做缓存？
可以用key-value 键值对存放。
key：唯一标识，例如 user:1001、note:2024
value：整行数据，一般存 JSON 字符串，把 MySQL 这一行所有字段打包成 JSON。
示例：note:101 → {"id":101,"title":"数据库笔记","content":"xxx"}

## 03耗时任务不想等, 怎么办? - RabbitMQ（任务存放）

1. # 除了我们刚才提到的“耗时任务等一下再处理”，通常还有什么样的情况和原因，会让一个项目引入 MQ？
(1).削峰填谷（流量限流）
短时间突发大量请求（比如秒杀、抢购），请求量远超服务器处理能力。把请求丢进 MQ，消费端按固定速度慢慢消费，防止瞬间流量压垮后端服务，保护系统。
(2).服务解耦
多个微服务之间不需要直接调用。比如订单创建成功后，要通知库存、短信、积分多个模块。订单服务只发一条消息到 MQ，库存、短信服务自己监听 MQ 拿消息处理。新增 / 删除下游服务，不用修改订单服务代码。
(3).消息广播（一对多通知）
一个事件触发，多个系统都要感知。例如用户注册成功，需要同时发送欢迎短信、开通会员、发送欢迎邮件，一条消息发给 MQ，多个消费者各自处理自己业务。
(4).最终一致性（分布式事务）
跨多个数据库的业务，保证数据最终一致。比如扣款成功后，异步发消息给 MQ，后续慢慢完成发货，不需要强同步锁等待。
(5).流量缓冲、异步重试
调用外部第三方接口不稳定，把任务放入 MQ，如果调用失败，MQ 可以重试这条消息，避免业务直接报错。

## 04.AI AI Agent
1. # AI Agent 是如何让大模型除了能以文本形式回答问题以外，还能进行更多操作的？
AI Agent 给大模型增加了工具调用（Tool Calling）能力。
过程：(1)预先定义好可用工具（读写文件、调用命令行、访问网页、发送消息等），并把工具的功能描述交给大模型；
    (2)大模型分析用户目标，判断单纯文字回答不够，就生成工具调用指令；
    (3)Agent 框架拿到指令，去执行对应的外部工具（操作电脑、生成文档、发消息）；
    (4)把工具返回的结果再交给大模型，大模型整理结果输出给用户。
2. # 长期使用一个 Agent 必然产生许多信息，而我们都知道大模型的 “记忆力” 是有限的。你有什么办法将这些大量信息存储起来呢？
（1）向量数据库（Vector DB）：把历史笔记、对话信息做向量化存储。当 Agent 需要时，检索相关片段，再把片段放进 prompt，实现长信息检索；(检索索引)
（2）普通文件 / 数据库：用本地文件（md、json）或者关系型数据库持久保存原始对话、笔记；
（3）记忆分层：区分短期记忆（当前对话上下文窗口）和长期记忆（外部存储）。短期记忆用完就丢弃，重要内容提取摘要存入外部存储；
（4）摘要压缩：对旧对话做总结提炼，只保存关键摘要，减少占用 token。
